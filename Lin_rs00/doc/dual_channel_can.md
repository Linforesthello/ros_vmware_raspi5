# R1 机械臂 — 双通道 CAN 架构分析

> 从对话历史提炼 · 2026-06-29
> 核心设计: 同一物理 CAN 总线，逻辑分两套 ID 空间

---

## 一、架构总图

```
N100 / RasPi5 (ROS2)
 │
 └── USB-CANable2 ──── 同一物理 CAN bus (500kbps)
                              │
      ┌── 逻辑通道#1: 低速状态机 ──┐
      │  接收 ID 0x1xx/0x2xx/0x3xx  │
      │  ── MCLM 状态帧 (50ms)     │
      │  ── SteeringArm 状态帧(50ms)│
      │  ── 原始数据，可交叉验证    │
      │                             │
      ├── 逻辑通道#2: 高速受信帧 ────┤
      │  接收 ID 0x4A0/0x4A1        │
      │  ── 网关融合帧 (10ms/100Hz) │
      │  ── 含车体vx/vy/omega+IMU  │
      │  ── RTOS确定步长，时间戳内置 │
      │                             │
      └── 控制指令  ────────────────┤
         发送 ID 0x125/0x130 等     │
         ── 发往MCLM/SteeringArm    │
                                    │
下层网关/主控 (RTOS, 确定步长)
 ├── CAN bus (本地, 0延迟ring buffer)
 ├── I2C (MPU6050+AK09911 9轴IMU)
 ├── SPI (MT6701 转向角, 可选)
 ├── 做运动学融合 (各电机→车体vx/vy/omega)
 ├── 发布高频融合帧 → CAN 0x4A0/0x4A1
 └── 安全监控、自主急停
```

---

## 二、两路数据对比

| 维度 | CAN#1 低速状态机 | CAN#2 高速受信帧 |
|:-----|:----------------|:----------------|
| **数据源** | 各控制器原始状态帧 | 网关融合处理后的数据 |
| **频率** | 20-50Hz | **100Hz** |
| **时基** | 各控制器各自时钟 | **网关统一 tick** |
| **内容** | 电机级原始速度/PWM/里程 | 车体级vx/vy/omega+IMU四元数 |
| **N100读取** | 被动接收 | 被动接收 |
| **用途** | 原始数据记录、交叉验证 | 控制回路主输入 |

### 数据对比示例

```
CAN#1 0x325:  speed=32, pwm=78, ticks=1200
CAN#1 0x326:  speed=-20, pwm=55
                                        ← N100可自己算运动学正解
CAN#2 0x4A0:  vx=0.48, vy=0.02, omega=0.49, tick=58231
CAN#2 0x4A1:  q=[0.99, 0.01, ...]
                                        ← 网关已经算好了
```

## 三、五大优势

### 1. 数据正交可验证

N100 同时拥有两套独立数据源。可以用 CAN#1 的原始速度自己算一遍运动学正解，与 CAN#2 的网关结果对比。

偏差超过阈值 → 知道网关或某个传感器有问题。

UART 方案做不到（数据只过一道手），单CAN全原始方案也做不到（没有融合后的对照）。

### 2. 高频与可靠性兼得

| 通道 | 频率上限 | 限制因素 |
|:-----|:--------:|:---------|
| CAN#1 原始帧 | 20Hz (50ms) | MCLM固件硬编码 |
| CAN#2 融合帧 | **100Hz (10ms)** | 网关本地融合，不依赖CAN查询 |

网关在 RTOS 内完成：IMU读取(I2C本地) + 运动学正解(纯运算) + 封帧发送。**不经过 N100 来回**，所以能做到 100Hz 确定性输出。

### 3. 网关价值被激活

```
改造前: UART↔CAN转发器 (可被N100直接取代)
改造后: 实时数据融合处理器
          ├── IMU姿态 (Mahony AHRS 9轴)
          ├── 运动学融合 (多电机→车体)
          ├── 时间戳对齐 (同源tick)
          └── 安全监控 (10ms响应)
```

UART 方案下网关是"必须经过的管道"。CAN 直连后如果网关只转发就无价值了。增加融合功能后，网关做的是 N100 (Linux非实时) 做不了的事。

### 4. N100 非实时性被隔离

N100 (Linux) 调度抖动通常有 1-10ms。如果直接参与 100Hz 控制回路，抖动会直接反映到控制质量。

双通道方案下 N100 **只被动接收** 100Hz 融合帧，控制回路的实时性由 RTOS 网关保证。N100 只负责 ~50ms 级的策略决策（轨迹规划、任务编排），对调度抖动不敏感。

### 5. 时间戳原生对齐

```
网关 10ms 定时器中断
 → 读 IMU (I2C, 本地, ~1ms)
 → 读 CAN ring buffer (最新MCLM状态, 本地0延迟)
 → 运动学正解
 → 封帧 → CAN 0x4A0 发送
 → 帧内自带 gateway_tick 时间戳
```

所有数据在同一 MCU、同一 tick 基准下融合，时间戳天然对齐，不需要 PTP 或 NTP 同步。对比：N100 自己读 MCLM 0x325 再读 IMU 串口，两个时间戳来自不同设备不同时钟，对齐要靠软件估算。

## 四、四大劣势与缓解

### 劣势1: 网关是单点

网关故障 → CAN#2 融合帧中断 → N100 高速通道失联。但 CAN#1 原始帧仍在。

**缓解**: N100 检测到 CAN#2 超时后降级：

```python
last_fusion = 0
while True:
    if recv_can2():
        last_fusion = now
        controller.update(融合数据)
    elif now - last_fusion > 0.5:  # 500ms 无融合帧
        controller.update(降级模式)  # 只用CAN#1原始数据自己做正解
        log.warn("网关融合帧超时，已降级")
```

### 劣势2: 单物理总线

CAN 总线物理断线 → 全系统失联。

**缓解**: CAN 差分对 (CAN_H/CAN_L) 物理可靠性远高于 UART 单端信号。收发器共模抑制比 > 70dB，断线概率在合理布线下极低。如需更高可靠性，可预留第二路物理 CAN 或无线备份。

### 劣势3: 网关改造工作量大

需要: 去掉UART + 集成IMU + 运动学算法 + 高频CAN发送。

**缓解**: 各子模块已存在独立代码：
- IMU: `6_Mpu6050_t1` 完整 Mahony 9轴实现
- 运动学: `plan/chassis_dual_type_support.md` 有公式和框架
- CAN发送: MCLM 的 `send_motor_status()` 可参考
- 去掉UART: 删掉 `ring_buffer.c` 和对应 handler

### 劣势4: 标准帧 8 字节限制

融合帧 8B 不够塞车体速度 + IMU 四元数。

**解决办法**（推荐拆两帧）:
- **0x4A0**: 车体速度 (vx/vy/omega + timestamp)
- **0x4A1**: IMU姿态 (四元数 + flags)

两帧交替发送或连续发送，N100 按序号合并。

## 五、方案 B：两路物理 CAN（预留）

```
CAN#1 (500k) ── MCLM/SteeringArm/RS00 ── 低速状态机
CAN#2 (500k) ── 网关发布融合帧         ── 高速受信通道

N100: 2×USB-CANable2
网关: 需换 STM32F3/F4/G4（有 2+ 个 CAN 外设）
```

| 对比 | 单总线逻辑分路 | 双物理总线 |
|:-----|:-------------|:-----------|
| N100硬件 | 1×CANable | 2×CANable |
| 网关 | F103够用 | 需换F3/F4 |
| 抗干扰 | 共享带宽 | 物理隔离 |
| 负载 | ~7.5% | 各~3% |
| 推荐 | ✅ 当前 | 未来扩展 |

**当前推荐单总线逻辑分路**，F103 够用，负载 < 10%，等需要更高性能时再考虑换 MCU。

## 六、IMU 集成位置

IMU (MPU6050+AK09911) 接在**网关板上 I2C 直连**是最优位置：

```
✅ 正确:
  ┌── 网关 ── IMU (I2C, 本地)
  │  靠近车体中心，不受线缆振动影响
  │  数据延迟 < 1ms

❌ 错误:
  N100 ── USB延长线 ── IMU
  线缆振动 + USB延迟 → 噪声
```

现有 `6_Mpu6050_t1` 已是 STM32 本地 I2C + FreeRTOS 的完整 9 轴 Mahony AHRS 实现，输出 ROS `sensor_msgs/Imu` 兼容格式，可直接集成到网关固件中。
