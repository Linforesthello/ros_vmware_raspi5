## 三、CAN 通信协议

### 3.1 CAN ID 分配表

| ID | 方向 | 用途 | 节点 | 频率 |
|:--:|:----:|:-----|:----|:----:|
| **0x101** | 广播 | 全车急停 | PC/网关→ALL | 事件 |
| **0x125** | → | 底盘转向电机指令 | PC→MCLM | 偶发 |
| **0x126** | → | 底盘动力电机指令 | PC→MCLM | 偶发 |
| **0x225** | ↔ | 底盘转向查询/应答 | PC↔MCLM | 按需 |
| **0x226** | ↔ | 底盘动力查询/应答 | PC↔MCLM | 按需 |
| **0x325** | ← | 底盘转向状态上报 | MCLM→总线 | **50ms** |
| **0x326** | ← | 底盘动力状态上报 | MCLM→总线 | **50ms** |
| **0x130** | → | 机械臂关节指令 | PC→Steering | 偶发 |
| **0x131** | → | 关节速度设置 | PC→Steering | 偶发 |
| **0x230** | → | 机械臂状态查询 | PC→Steering | 按需 |
| **0x330** | ← | 机械臂状态上报 | Steering→总线 | **50ms** |
| **0x430** | → | 机械臂参数配置 | PC→Steering | 偶发 |
| **0x4A0** | ← | **网关融合帧(高优先级)** | **网关→总线** | **10ms** |
| **0x4A1** | ← | 网关事件帧 | 网关→总线 | 事件 |
| **RS00 私有** | ↔ | 扩展帧29-bit, 不冲突 | PC↔RS00 | 按需 |

### 3.2 网关融合帧 (0x4A0, 10ms, 100Hz)

```
Byte 0:     帧序号 (uint8, 自增, 用于N100检测丢帧)
Byte 1~2:   timestamp_tick (uint16, 网关系统tick, 10ms分辨率)
Byte 3~4:   车体 vx  (int16, 0.01m/s, 范围 ±10m/s)
Byte 5~6:   车体 vy  (int16, 0.01m/s, 范围 ±10m/s)
Byte 7~8:   车体 omega (int16, 0.01rad/s, 范围 ±30rad/s)
Byte 9~12:  IMU 姿态四元数 w (int16, 0.001精度)
Byte 13~14: IMU 姿态四元数 x (int16, 0.001精度)
Byte 15:    标志位 (bit0: IMU有效, bit1: 急停, bit2: 底盘失联)
```

> 标准CAN帧仅8字节，一帧塞不下。方案：
> - 拆分两帧：0x4A0 车体速度 (8B) + 0x4A1 IMU姿态+标志 (8B)
> - 或改用CAN FD（F103不支持）
> - **推荐**: 两帧交替或连续发，N100合并

### 3.3 总线负载估算

| 帧来源 | 帧数/s | 带宽占用 |
|:-------|:------:|:--------:|
| MCLM 325/326 | 40 | ~1.0% |
| Steering 330 | 20 | ~0.5% |
| 网关 4A0/4A1 | 200 | ~5.0% |
| 控制指令 | ~20 | ~0.5% |
| RS00 扩展帧 | ~20 | ~0.5% |
| **合计** | **~300** | **~7.5%** |

500kbps 下限幅 **10% 以内，完全充足**。

## 四、双通道CAN架构利弊分析

### 核心思想

同一物理CAN总线，逻辑分两套ID空间：

- **低速状态机 (ID 0x1xx/0x2xx/0x3xx)**: N100直接读各控制器原始状态帧，数据未经过处理，用于交叉验证网关的正确性
- **高速受信帧 (ID 0x4xx)**: 网关用RTOS确定步长发布融合后高频数据（含IMU），N100被动接收，不依赖Linux实时性

### 优势

| # | 优势 | 说明 |
|:-:|:-----|:------|
| 1 | **数据正交可验证** | N100同时有原始电机速度+网关融合结果，能交叉校验 |
| 2 | **高频+可靠兼得** | 100Hz融合帧来自RTOS(确定步长)，不受Linux调度抖动影响 |
| 3 | **网关价值激活** | 不再是"转发器"，而是"实时数据融合处理器"(IMU+运动学) |
| 4 | **N100非实时隔离** | 只被动接收，不发高频查询，Linux调度延迟不影响数据连续性 |
| 5 | **时间戳原生对齐** | IMU和电机数据在同一MCU内融合，同源tick，无需PTP同步 |
| 6 | **IMU位置合理** | 接在网关板上I2C直连，靠近车体中心，不受USB线缆振动影响 |
| 7 | **硬件无增加** | 同一物理CAN总线，逻辑ID分开，F103单CAN外设足够 |

### 劣势

| # | 劣势 | 缓解 |
|:-:|:-----|:------|
| 1 | **网关是单点** | 网关故障→失去融合帧，但N100可从CAN#1读原始数据降级运行 |
| 2 | **同一物理总线** | 物理断线全系统失联（CAN差分可靠性远高于UART，实际风险低） |
| 3 | **网关改造工作量大** | 需整合IMU+运动学+高频CAN发送，去掉UART逻辑 |
| 4 | **融合帧跨8字节** | 标准帧8B不够，需拆两帧或压缩精度 |
